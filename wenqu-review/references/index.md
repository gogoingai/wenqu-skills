# 审查流程入口

## 核心规则

**修改后要重新审查一遍，但 R0、R5、R1、R2、R3 与 R7 的执行节奏不同**：

- R5、R1、R2、R3 是语言层审查，成本低，每次修改完都可以照常跑一遍，包括连贯性检查——局部改动可能破坏上下文衔接或造成前后不一致，只重审改动片段会遗漏这类问题，**这四项永远要跑全篇，不是只看改动处**。
- **R0 成本高**（要重新跑脚本、读源码、逐条核对），单次会话里如果是连续的小修改或来回调整，**不要每改一次都跑一次 R0**。执行阶段新增的 claim 应该已经在改之前核实过源码；R0 留到这一轮编辑收尾时（用户给出"审查一下""可以了""先这样"之类的收尾信号，或者明确要求查一遍）再统一跑一次，把本次会话里新增、尚未核实的 claim 一并核对，已经核实过的部分不必重复检查。涉及评测时，R0 还要检查比较条件与结论边界，不能把单个数字当成泛化证明。
- **R7** 只在术语、机制、数字、范围、标题、章节结构或图片发生实质变化后运行；它检查改动是否在全文及图文中同步到位，不替代语言审查或事实核验。

## 审查顺序

**默认自动模式：触发时按 R0→R5→R1→R2→R3 一次跑完，发现问题直接修，全部完成后统一汇报结果。用户说"手动审查"时才切换为每步等确认。**

| 步骤 | 文件 | 内容 | 何时跑 |
|------|------|------|-------|
| R0 | `r0-factcheck.md` | 来源、真实性与评测叙事核查 | 留到收尾时跑一次，不用每次小修改都跑 |
| R5 | `r5-coherence.md` | 连贯性 + 清晰度（先整体读一遍） | 每次修改完都可以跑 |
| R1 | `r1-english.md` | 英文术语检查 | 每次修改完都可以跑 |
| R2 | `r2-translation.md` | 翻译腔审查 | 每次修改完都可以跑 |
| R3 | `r3-ai-patterns.md` | 模式化与空泛表达 | 每次修改完都可以跑 |
| R4 | `r4-structure.md` | 结构自检 | 用户说"完整审查"时才跑 |
| R6 | `r6-style-and-narrative-fit.md` | 文体与叙事契合 | 用户说"完整审查"时才跑 |
| R7 | `r7-change-closure.md` | 变更闭环与全篇一致性 | 实质改动收尾、提交前或完整审查时跑 |

> R0 单独成本高，是因为它要逐条对照源码核实数字、字段名、机制描述，往往要重新读文件甚至跑脚本验证。这和 R5、R1、R2、R3 只读文本判断语言问题不是一个量级，所以不能套用同一个"每次都跑"的节奏。真正跑 R0 时它排在最前面：事实错误比语言问题更危险，要先确认内容属实，再打磨表达。R5 紧随其后，结构性断层要先发现出来，后面的逐条检查建立在内容连贯的基础上。R4 与 R6 默认跳过：R4 检查骨架，R6 需要结合已确认的题材和写作目标判断，用户要求完整审查时再一起执行。R7 放在全部修复之后，负责检查改动是否残留旧术语、旧结论、旧图示或旧交叉引用。

## 触发

用户说"审查"、"看看有没有问题"、"检查一下"、"整体看看"、"review"，或提供文章路径要求质检。

不需要问：读者类型、发布平台、写作目的——文章已有，不需要再问。

## 报告格式规范

每步结束给出清晰报告：

- **发现问题**：行号 | 当前写法 | 候选改法（1-2个）
- **未发现问题**：一句话确认"X 项均无问题"
- **候选之间**：说明语感差异，让用户选择
