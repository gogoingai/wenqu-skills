# 素材收集执行手册

四步流程（规划 → 搜索 → 下载 → 整理）每一步的具体执行方法。`SKILL.md` 是概览，本文件是操作细则。

## 第 1 步：规划

**输入**：题目方向、写作目标、目标读者、范围锁定、已明确的关键词/模块名（来自 wenqu-write Step 1/1.5，或用户直接给出）。

**产出：收集清单**（内容范围的唯一确认点），格式：

```markdown
## 收集清单

### 相似文章（写法参考，找 2~4 篇）
| 想找什么 | 搜索关键词 |
| --- | --- |
| 讲 XX 系统的技术长文，结构偏源码拆解 | "XX 源码解析"、"XX deep dive"、"XX 原理" |
| 面向中级工程师的 XX 入门到实践 | "XX 入门 实践"、"getting started XX production" |

### 相关素材（事实素材，按需）
| 想找什么 | 搜索关键词 | 预期来源 |
| --- | --- | --- |
| XX 的官方设计文档 | "XX design doc"、"XX architecture" | 官网/GitHub |
| XX 的容量/性能数字 | "XX benchmark"、"XX 性能测试" | 官方博客/论文 |
| 公众号上的 XX 实践分享 | "XX 实践 公众号" | mp.weixin.qq.com |
```

执行要点：

1. **相似文章先于相关素材**——先看别人怎么切题，再决定还缺什么料。
2. 关键词中英文各准备 2~3 组，覆盖同义表达。
3. 清单给用户确认时说明预计抓取数量；范围锁定里明确排除的内容不安排搜索。
4. CLI 安装授权不属于内容范围确认：只有检测到缺失增强项时才提示，且只请求一次授权。

## 增强 CLI 检查、授权与降级

每次收集流程开始时，agent 检查 `open-websearch`、`crwl`、`crawl4ai-setup` 和 `crawl4ai-doctor` 是否可直接调用；用户级全局安装但未进入 PATH 的命令，agent 使用已发现的绝对路径或本轮 PATH，不要求用户修改 shell 配置。

- `open-websearch` 已可调用：作为搜索补充项使用。
- Crawl4AI 的三个命令都可调用：作为下载增强项使用；首次或最近失败后先运行 `crawl4ai-doctor`。
- 有任一项缺失或健康检查失败：agent 发出一次清晰的授权提示，列出缺失项及副作用，例如：

  > 我可以现在为后续素材收集安装增强 CLI：`open-websearch` 用于补充多引擎搜索，Crawl4AI 的 `crwl` 用于下载动态页面和公众号；后者还会下载浏览器运行环境。安装、浏览器设置和健康检查都由我完成。是否授权我现在安装缺失项？

- 用户明确授权后，agent 自行执行并验证：

  ```bash
  npm install -g open-websearch
  uv tool install --upgrade crawl4ai
  crawl4ai-setup
  crawl4ai-doctor
  ```

  `uv` 不可用时，agent 改用 `python3 -m pip install --user -U crawl4ai` 提供用户级全局 CLI；若该路径也不可用，记录安装失败并继续原生流程。安装完成后，agent 自行确认 `open-websearch` 能输出 JSON 搜索结果、`crawl4ai-doctor` 成功且 `crwl` 能抓取一个公开页面。

- 用户拒绝、安装失败或验证失败：agent 不要求用户复制命令、配置 PATH 或排障；搜索继续使用 agent 自带的联网搜索工具，下载继续使用 agent 自带抓取，并把不可用原因写入本轮失败记录。

不启动 `open-websearch` daemon，不配置 MCP，不使用 `npx`，也不使用 Crawl4AI Python API。

## 第 2 步：搜索与候选合并

1. **先跑原生搜索**：对清单中每组关键词使用 agent 自带的联网搜索工具；这是每轮必跑的基础候选集。每组取前 3~5 条，记录标题、URL、一句话相关性与检索渠道 `agent-native`。
2. **再跑可选补充搜索**：`open-websearch` 可调用时，对相同关键词运行其 CLI；解析 JSON 结果，记录引擎名为 `open-websearch:{engine}`。单个搜索引擎失败时保留其他引擎结果和失败信息；只有 CLI 无结果或整体失败时才不新增候选，不影响原生搜索。
3. **按食谱恢复浏览器检索**：仅当一个已请求的直连引擎失败或无候选，且 `crawl4ai/search-recovery.md` 为该引擎定义了食谱时，才用 `crwl` 对同一关键词执行一次浏览器检索。成功候选标为 `crwl-serp:{engine}`；验证页、登录页、付费墙、空结果或无法还原原始 URL 时只记录失败，不重试轰炸，也不绕过访问控制。公众号发现使用独立的同会话食谱，不能把搜狗跳转链接交给另一条命令重放。
4. **统一去重后再下载**：合并原生、直连补充和浏览器恢复候选，先按规范化 URL 去重，再按内容标题与正文摘要辅助识别同文转载。规范化时移除 fragment 与常见追踪参数；不得改写带签名的 URL 或微信公众号 `src=11` 入口。重复项保留一条候选，并合并全部检索渠道。
5. **统一分级**：官方文档/源码 > 官方博客 > 知名技术媒体 > 个人博客 > 内容农场；同内容转载优先保留原始出处。只在合并、去重和分级后安排下载，不再让用户逐条确认。
6. 用户直接提供 URL 时不做检索；该条标为 `用户提供`，仍与搜索候选一起去重和分级。
7. 原生搜索连续两轮找不到满意结果时，在清单上标注“未找到，待用户补充”，不硬凑低质量来源。
8. **论文/研究报告例外**：先由 agent 原生搜索按题名、作者、DOI、会议/期刊和年份定位论文 PDF 或官方落地页；`open-websearch` 没有学术专用引擎，只能补充解读与外围候选。具体边界见 `open-websearch/engines.md`。

## 第 3 步：下载

可用时使用 `crwl`，产物直接落到本篇素材目录对应分类下；完整命令、配置边界与失败处理见 `crawl4ai/cli.md`，公众号路径见 `crawl4ai/site-recipes.md`。`open-websearch` 的完整引擎选择、CLI 协议与安装边界分别见 `open-websearch/engines.md`、`open-websearch/cli.md`、`open-websearch/setup.md`。

```bash
# 单页
crwl <url> -o markdown -O {materials}/articles/<域名>/<slug>.md

# 整站/文档站（产物是合并单文件，====== 分隔）
crwl <url> --deep-crawl bfs --max-pages <N> -o markdown -O {materials}/docs/<站点>.md
```

- `crwl` 不可用、健康检查失败或某页抓取失败时，agent 自动改用原生下载；不能因增强项失败放弃该候选。
- 批量下载逐个串行执行，避免浏览器实例争抢资源或触发反爬。
- 边抓边登记：每成功一项即写 URL、检索渠道与文件路径；失败也登记 URL、实际下载方式和原因。
- 文件命名：`articles/` 下按来源域名建二级目录，文件名用内容 slug，不用随机串。

## 第 4 步：整理

1. 通读下载产物写摘要，写清“讲了什么、对本篇有什么用”，不抄标题。
2. 登记 `index.md`：按 `SKILL.md` 填全来源类型、来源、**检索渠道**、文件路径、用途、标签和关联章节。
3. 与全局文库和本篇已下载内容去重；下载产物重复时只保留一份文件，但在素材条目的检索渠道列保留所有发现路径。
4. 可跨文章复用的条目提炼成 L 条目回收至全局文库；原始文件仍留在本篇素材目录。
5. 收尾向用户简要汇报：原生与增强搜索各带来多少候选、合并后保留多少素材、下载成功/失败数量、增强项是否启用及失败清单。
