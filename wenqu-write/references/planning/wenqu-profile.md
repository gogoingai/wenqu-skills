# 写作画像、设计决策图与章节职责卡

这份文件为骨架、R6 与实质修改提供共同基准。它不替代读者画像：读者画像回答“写给谁”，写作画像回答“以什么题材、什么叙事方式写”。

## 一、写作画像

骨架前确认以下内容，并写入文章存储的 `SKILL.md`。

| 项目 | 需要确认的内容 |
|------|----------------|
| 题材 | 自研技术方案介绍、源码解析/外部项目介绍、论文/研究报告、产品说明/使用指南；混合题材注明主次 |
| 核心目标 | 读者最终应理解、判断或完成什么 |
| 叙事主体 | 关键选择由谁作出；机制说明由架构、链路、模块还是代码事实承担 |
| 表达尺度 | 哪些术语、公式、案例和背景解释是必要的，哪些不应展开 |

### 题材与表达边界

| 题材 | 应重点呈现 | 不应误用的表达 |
|------|------------|----------------|
| 自研技术方案介绍 | 真实问题、取舍、实现、边界与验证 | 把所有选择藏进笼统的“系统会……”；只列能力不讲判断 |
| 源码解析 / 外部项目介绍 | 可核查代码事实、模块职责、实际行为 | 把推测写成原作者动机或“我们为何这样选” |
| 论文 / 研究报告 | 问题定义、方法、论证、实验与限制 | 为了口语化而删掉必要定义、方法或限制 |
| 产品说明 / 使用指南 | 用户任务、能力边界、操作与预期结果 | 堆砌不服务于使用决策的内部细节 |

## 二、设计决策图

仅用于自研技术方案介绍、技术决策复盘，或混合题材中以此为主的部分。它不是正文模板，而是防止文章沦为能力清单的规划工具。

```markdown
## 设计决策图
| 能力 / 决策 | 实际问题 | 备选或不采用的做法 | 我们的选择 | 实现机制 | 边界 / 验证 | 素材依据 |
|-------------|----------|------------------|------------|----------|-------------|----------|
| ... | ... | ... | ... | ... | ... | M1, M5 |
```

只记录文章准备重点展开的选择，不把所有模块都塞进表。正文在需要表达选择时可以写“我们将……”；日常机制描述应以具体架构、链路或模块为主体。

## 三、章节职责卡

骨架中的每个主要章节补充三行：

```markdown
回答：本节让读者解决的一个问题
不重复：已在何处讲过、这里不再展开什么
衔接：本节给出什么前提，下一节为何自然接上
```

它用于提前发现章节重复、概念提前出现或过渡断裂。纯目录、参考文献等非叙事章节可省略。
