# 内容来源与评测叙事

技术文章中的一句话不一定都来自同一种依据。写入 `materials.md` 时先标明来源类型；正文也按它的边界表达，避免把设计意图、外部结论或帮助理解的例子写成已经实现的事实。

| 来源类型 | 可写什么 | 必要依据与表述边界 |
| --- | --- | --- |
| 实现事实 | 已有代码、配置、运行结果实际做了什么 | 对应源码、配置或可复现运行记录；不能把计划写成现状 |
| 团队选择 | 为什么采用某种架构、规则或取舍 | 已确认的设计说明或用户提供的决策；可写“我们将……”，但不虚构动机 |
| 外部研究 | 论文、文档、公开资料提供的背景或方法 | 标注来源与适用条件；不能直接证明本项目已经具备同样效果 |
| 合理推断 | 基于已知材料得出的解释或可能影响 | 明确“可推断”“可能”；不得伪装为源码事实 |
| 简化场景 | 用于帮助读者理解机制的虚构情境 | 明确是简化场景；不使用看似真实的业务数字、人物或效果结论 |

## 评测叙事

出现评测数字、对比结论或“效果更好”时，在 `materials.md` 追加一条评测设计，至少写清：

- **评测对象：** 测的是哪一段链路或哪项能力；
- **比较条件：** 对照对象、输入规模、样本范围、阈值和时间口径是否一致；
- **指标含义：** 数字实际衡量什么，不衡量什么；
- **可证明范围：** 结果能支持哪一条设计判断；
- **不可外推范围：** 不得据此泛化到哪些用户、场景或系统能力。

材料不足以说明这些边界时，收窄正文结论或标为待确认；不要为了让评测段“完整”补造条件。
