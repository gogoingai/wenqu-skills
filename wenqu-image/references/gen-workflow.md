# 图片生成工作流

> 本文件是 wenqu-image 技能的核心执行流程，进入「生成图片」阶段后加载。
> 触发词：「生成图片」「把图画出来」「渲染一下」「帮我生图」。

---

## 基本原则

逐张生成、逐张确认，不批量、不跳过用户。每张图经过自动质检后再给用户看，用户确认后再写入文章，再进入下一张。

**重新设计/改版时，先给方案再生成**：如果是用户反馈某张图不满意要求重做（不是第一次生成全新图），先用文字简述新方案（结构、节点、信息密度安排），等用户确认方向没问题，再调用图片 CLI。直接生成再展示结果的方式，在方向没对齐时会导致反复返工。仅当用户明确说"直接生成/不用确认"时跳过这一步。

**⚠️ 逐张生成必须串行**：Codex 路径靠"生成前后对比 codex session 文件"来找到自己的输出，并行会互相抢结果；其他后端虽无此限制，也必须等当前图质检、上传、用户确认后再处理下一张，避免文章版本与反馈串图。

---

## 第一步：检测并配置环境

优先运行一次图片 CLI 的环境检测。它检查 Bun、Codex、PicGo 和四个后端的密钥状态；输出不含密钥。不需要另行安装 `gpt-image-2` skill：

```bash
bun ~/.agents/skills/wenqu-image/scripts/image-cli/main.ts --check --json
```

按 `runtime` 与 `providers` 字段判断当前可用路径；Codex 使用当前登录态，OpenAI、通义和 Seedream 的密钥只从 `~/.gogoingai/wenqu-skills/image/.env` 读取。配置格式和模型能力见 `image-cli.md`。

若检测到缺失依赖，按下表手动确认：

| 工具 | 验证命令 | 缺失时 |
|------|---------|--------|
| `bun` 或 `npx` | `bun --version` | 推荐 `brew install oven-sh/bun/bun`；没有 Bun 时，用 `npx -y bun` 运行同一 CLI |
| `codex` CLI（仅 Codex 路径） | `codex --version` | 安装 Codex CLI 并运行 `codex login` |
| `picgo` | `picgo --version` | `npm install -g picgo` 或 `brew install picgo` |

picgo 图床配置：运行 `picgo set uploader` 按提示填写图床信息；配置后 `picgo upload 任意图片.png` 验证，看到 `https://` 开头的 URL 说明成功。

PicGo GUI 用户需先让 PicGo CLI 使用同一 uploader；图片 CLI 不会自动安装、同步或修改图床配置。

## 第二步：列出所有画图点，先补全占位标记

扫描文章中两类画图标记：

1. **占位标记**（写作阶段留下的轻量标记，尚未确定具体画法）：`> 🖼️ 待配图：[一句话描述]`
2. **完整画图提示**（`# 画图提示` 代码块，规范已写全，正文前带 `style:` YAML frontmatter）

**先查本篇偏好库**（`{项目根目录}/wenqu-skills/{文件名}/references/preferences.md`「配图偏好」表，没有则跳过这一步）——有已记录的默认风格/配色规则，转换占位标记时直接套用，不重复问用户。

**先处理占位标记，逐条转换成完整画图提示**：读该占位标记所在小节的正文内容，参考 `diagram-type-selector.md`（该画哪类图）选定类型后，去对应的 `templates/*.md` 取 prompt 骨架，配色审美另见 `design-principles.md`，写出完整 `# 画图提示` 代码块（含 `style:` frontmatter，格式见 SKILL.md「与调用方的接口约定」），替换掉原占位标记的位置。转换结果先用 `AskUserQuestion` 工具给用户看一眼图类型和大致结构，等确认后再生成，除非用户已明确说"直接生成不用确认"。

转换完所有占位标记后，统一列出全文所有 `# 画图提示` 代码块，同时检查每个代码块之后是否已有 `<img>` 标签，按顺序列出状态：

- ✅ 已有图片（显示现有 URL，用 `AskUserQuestion` 询问是否需要因内容变更而重画）
- ⬜ 待生成

只对"待生成"的图执行后续步骤；"已有图片"的默认跳过，除非用户明确要更新。告知用户共 N 张待生成、每张约 1～3 分钟，用 `AskUserQuestion` 询问是否现在开始或跳过某几张。

## 第三步：逐张生成、质检、确认

### 3.1 生成图片

提取该画图提示代码块文本（去掉 YAML frontmatter 和 `# ` 前缀，只保留提示正文——frontmatter 是给人和技能自己看的风格标记，不发给生图模型），**两步执行，不能合并**。

**每次生成都用新的随机文件名**（不管是第一次生成还是重新生成/改图）：文件名前缀统一用 `article-img`，随机后缀用 `RAND=$(openssl rand -hex 8)`（16 位十六进制，比旧版更长，避免碰撞）。`/tmp` 下的文件只用于本轮生成、质检与上传，**不得写入文章、`ref` 或 `versions`**。不复用旧文件名去覆盖 CDN——每一版图片都要有自己独立的 HTTPS URL，才能在文章的 `versions` 版本数组里保留、回看每一版（见第四步）：

```bash
# 生成并上传；provider/model 未指定时读取本篇或全局配置
RAND=$(openssl rand -hex 8)
bun ~/.agents/skills/wenqu-image/scripts/image-cli/main.ts \
  --prompt "提示文本" \
  --out /tmp/article-img-${RAND}.png \
  --article-config "{项目根目录}/wenqu-skills/{文件名}/config/image.json" \
  --upload
# 输出的 https:// URL 即为这一版的 CDN 地址；上传失败时只保留本地文件
```

重新生成/改图时同样跑一遍上面命令，`--prompt`（或图改模式的 `--ref`）换成调整后的内容，`RAND` 照常重新生成一个新的，**不要沿用旧图的文件名**。需要覆盖全局选择时，加 `--provider` 与 `--model`；不得在命令或文章中携带密钥。

> **本轮生成的每一版 HTTPS URL 都要记下来**（哪怕质检不通过、用户否决），先在对话里临时记着，第四步写入文章时一并追加进 `versions` 数组——不要生成完不满意就把 URL 丢掉不管，那一版可能后面还有对比价值。上传失败的本地文件不属于版本，不得写入历史。

### 3.2 自动质检

质检分两个阶段，**第一阶段优先级最高**：

#### 第一阶段：用户迭代要求清单（每次重新生成前必做）

每次用户指出问题，立刻把要求写成清单条目。下次生成后，**先逐条核对这张清单，再做常规质检**。清单里每一条都要明确写「✅ 已修复」或「❌ 未修复」，未修复即不通过，不能跳过。

> 常见踩坑：用户说"删掉这个箭头"——生成后只看整体觉得差不多就过了，没有专门去找那个箭头有没有消失。**必须专门找它，确认消失再过。**

**典型需要追踪的要求类型：**
- 「删除 X 元素」→ 专门确认 X 不在图中
- 「统一箭头颜色」→ 逐条检查所有箭头颜色一致
- 「不要出现 [Image N] 标签」→ 扫描全图有无方括号文字
- 「X 不能连回图内节点」→ 追踪 X 的终点确认出图
- 「是/否标签在正确分支」→ 逐个菱形节点核对两条分支的标签

#### 第二阶段：常规质检

| 检查项 | 具体内容 |
|--------|---------|
| **完整性** | 所有节点、标签、箭头是否都出现？有无漏掉的元素？ |
| **文字准确性** | 逐字读一遍：有无错字（形近字替换如「则→侧」）、乱码、截断、英文混入？重点查多笔画汉字 |
| **连接正确性** | 每条箭头逐一核对：①起点 ②终点 ③方向 ④标注文字 ⑤「是/否」挂在哪个分支（不能只看箭头存在，必须确认方向和终点） ⑥有无悬空节点 ⑦回环/旁路是否真正连到目标 |
| **多余元素** | 图中每个元素是否都在提示词里有依据？尤其检查：`--ref` 改图时旧元素残留、模型自动加的 `[Image N]` 标签、用户要求删除的元素是否真的消失 |
| **视觉整洁度** | 箭头颜色是否统一（用户要求统一时必查）；有无留白失衡、节点拥挤、线条覆盖 |
| **反模式** | 泳道图、旁路悬空、列间箭头乱、层间扇形展开、节点流水编号、终点节点有多余出发箭头 |

质检结果分三档：通过 → 3.3；有瑕疵但可接受 → 附说明展示给用户；有明显问题 → **直接进入 3.3b 自动修复重试，不停下来问用户，但每次都打印 URL**。

> **质检是强制步骤，与生成路径无关**：无论是首次生成、还是通过图片 CLI 的 `--ref` 图改模式，每次生成后都必须完整执行 3.2 质检并输出质检结论，不能因为"切了路径"就跳过。

### 3.3 先上传，再展示给用户确认

**先上传拿到 URL，再让用户确认**——不要等用户确认后才上传，上传有时间成本。**质检不通过时也要上传**——用户需要看到实际图片才能判断是否接受瑕疵，不要因为质检失败就只给文字描述。

**必须用 `AskUserQuestion` 工具提问，不得只输出文本等用户手打回复**。图片本身放进选项的 `preview` 字段（`preview` 按 markdown 渲染，用 `![标题](CDN URL)` 加质检结论），让用户在同一个界面里看图做选择，不要把图片单独发一遍纯文本再问：

```json
{
  "questions": [{
    "question": "第 N 张 / 共 M 张：[图片标题] —— 质检结论：✅ 通过 / ❌ 未通过 / ⚠️ 有以下瑕疵：[简述]（样式得分 X/10）",
    "header": "图片确认",
    "multiSelect": false,
    "options": [
      {
        "label": "确认，写入文章",
        "description": "采用这一版，写入文章后继续下一张",
        "preview": "![图片标题](CDN URL)\n\n质检：✅ 通过 / ⚠️ 瑕疵：[简述]\n样式得分：X/10 — [亮点/扣分点]"
      },
      {
        "label": "重新生成",
        "description": "保留这版作为历史版本，根据反馈调整提示词重新生成（最多 2 次额外重试）"
      },
      {
        "label": "跳过这张",
        "description": "代码块保留，不插入图片，先处理下一张"
      }
    ]
  }]
}
```

用户选"确认，写入文章" → 写入文章（见第四步），继续下一张
用户选"重新生成" → 用户若未在选择时说明具体问题，追问一句"哪里不对"，再据此调整提示词，回到 3.1
用户选"跳过这张" → 代码块保留，不插入图片，继续下一张

### 3.3b 自动修复重试（质检不通过时）

**先判断问题类型，再选修复路径：**

| 问题类型 | 说明 | 修复路径 |
|---------|------|---------|
| **视觉/文字问题** | 文字错误、配色不对、元素缺失、留白失衡 | 用 `--ref` 在原图基础上改（见下方"图改模式"） |
| **结构/箭头问题** | 箭头方向错、连接关系错、布局错 | 重写提示词重新生成（`--ref` 无法可靠修改结构） |

> **`--ref` 的能力边界与两难**：`--ref` 能保留视觉风格（配色、图标、卡片设计），适合改文字、换颜色、调细节。但结构改动（箭头方向、连接关系、布局）往往无效——模型会照抄原图结构。反过来，不用 `--ref` 重新生成，结构可以按提示词改，但视觉风格很难完全复现。
>
> **遇到"想保留风格 + 修结构"时**：这是 GPT Image 2 当前的能力边界，没有完美解法。建议方案：
> 1. 先用 `--ref` 多试几次（偶尔能改成功）
> 2. 若多次无效，用 `AskUserQuestion` 把选择权交给用户，两个选项各带 `preview`（风格版 vs 结构正确版的图片+说明），不要无限循环重试：a) 接受原图风格但结构有瑕疵；b) 接受重新生成的结构正确但风格略有差异

**图改模式（视觉/文字问题时使用）：**

```bash
# 1. 用图片 CLI 以原图为参考修改，输出文件名同样用新的随机后缀
RAND=$(openssl rand -hex 8)
bun ~/.agents/skills/wenqu-image/scripts/image-cli/main.ts \
  --prompt "在这张图基础上只改：[具体说明改什么]，其他完全保持原样" \
  --ref /tmp/原图.png \
  --out /tmp/article-img-${RAND}.png \
  --upload
# 输出的 https:// URL 即为这一版的 CDN 地址
```

> 用了 `--ref` 就要记住这次实际传的参考图是什么：已采用图记录其 CDN URL，风格库图记录 GitHub raw URL（`wenqu-image-assets/styles/` 下对应图的 raw 地址）。命令可临时传入 `fetch-ref.sh` 下载到 `~/.cache/` 或 `/tmp` 的本地文件，但**本地路径不得写入 `ref:` 字段**（见第四步）。

**重新生成时的常见修复策略：**

| 检测到的问题 | 修复策略 |
|-------------|---------|
| 泳道图结构 | 改用「N 张卡片从左到右水平排列，卡片之间用粗箭头连接，禁止使用泳道/等高列结构」 |
| 旁路节点悬空 | 对每条旁路末端加「→ 向下连入「[汇合节点名]」」 |
| 列间箭头混乱 | 添加独立「列间连接」段落，逐一声明每列出口连到哪列入口 |
| 多列布局内节点各自出箭头 | 列内的子节点不要各自引出箭头到下一列；改成「列/模块之间用一条整体箭头连接，列内子节点只在列内排列，不单独出箭头」——这样箭头数量少、不交叉、视觉更干净 |
| 层间箭头扇形展开 | 加「每层之间只画一条居中垂直向下箭头，不展开连到各节点」 |
| 文字截断或乱码 | 缩短单节点文字，拆分过长标签 |
| 节点有流水编号 | 加「节点不加流水序号，除非画图提示明确要求」 |
| 金字塔层序画反 | 加「底部最宽为第一层，顶部尖顶为第 N 层，从下到上编号递增」 |
| 留白失衡 | 减少某区域节点数量，或拆分密集节点为简洁描述 |
| 终点节点多出一条出发箭头 | 提示词里若没有明确说「此节点引出箭头」，终点节点不得有出发箭头——在提示词里加「此节点无出发箭头，是流程终点」 |
| 箭头颜色不统一 | 用户说「统一颜色」时，在提示词里指定「所有箭头统一为深灰色，不得出现蓝/绿/紫/红混色」 |

最多自动重试 **3 次**（含第一次）。3 次后仍有问题 → 3.3c。

### 3.3c 三次均未通过：询问用户

**必须用 `AskUserQuestion` 工具提问**，把最近一版图片放进 `preview` 字段，让用户边看图边选：

```json
{
  "questions": [{
    "question": "自动修复 3 次后仍有问题：[问题描述]",
    "header": "多次未通过",
    "multiSelect": false,
    "options": [
      {"label": "接受这张", "description": "有瑕疵但够用，直接采用最近一版", "preview": "![最近一次结果](最近一次 URL)\n\n遗留问题：[问题描述]"},
      {"label": "我来重新描述", "description": "告诉我具体哪里不对，我据此重新生成"},
      {"label": "跳过这张", "description": "代码块保留，不插入图片，暂时留空"},
      {"label": "查看 3 次结果我来选", "description": "列出 3 次生成的 URL，由用户从中挑一张采用"}
    ]
  }]
}
```

用户选"查看 3 次结果我来选" → 追加展示 3 次生成的 URL 列表（可再发一轮 `AskUserQuestion`，每个选项 `preview` 对应一版），由用户指定采用哪一版

## 第四步：写入文章

**写入前必须先读当前文章内容**，检查该画图提示代码块是否被人工修改过（与本次生成时提取的版本不同）：

- **代码块未改动**：正常写入，无需提示
- **代码块已被人工改动**：展示 diff，用 `AskUserQuestion` 询问「检测到画图提示已被手动修改，是否用当前版本覆盖，还是保留你的修改？」（选项：用当前版本覆盖 / 保留我的修改），等用户确认再操作

同理，若文章中已有图片（重新生成场景），不再判断"URL 是否相同可跳过"——每一版现在都是独立文件名/独立 URL，一律走下面的 `versions` 追加逻辑。

写入时，**必须做以下几件事，缺一不可**：
1. 把最终成功的提示词回写到文章代码块（哪怕只改了一个字也要更新）——提示词是图片的"源码"，内容变更重新生成时用的是最新版
2. `ref` 字段**只在本轮实际用了 `--ref`（风格参考图或图改模式）时才更新**：风格资产写稳定相对路径，已采用图写 HTTPS CDN URL；**本地路径、`file://` 与 `/tmp` 一律不得写入**。本轮没用 `--ref` 时，保持原值不动，不要清空或删除这一行。
3. 把本轮上传成功的**每一版 HTTPS CDN URL**（含质检不通过、用户否决的版本）追加进 frontmatter 的 `versions` 数组，编号接着已有的最大版本号往后延续，**不删除、不覆盖任何一条已有记录**，每条带一句简要说明（初版/否决原因/最终采用等）；同编号追加 `generation.vN.provider` 与 `generation.vN.model`。本地文件和上传失败结果不得进入历史
4. 把 `![标题](URL)` 更新为用户最终确认采用的那一版 URL；若这一轮用户选 C（跳过）或还没确认，`versions` 照样追加，但 `![]()` 保留上一次确认过的版本，不指向未确认的新版本

常见漏洞：只插了 URL 没更新代码块；忘了把否决的版本也记进 `versions`；把 `/tmp`、绝对路径或 `file://` 写进 `ref` / `versions`；`ref` 没变化却被误清空。写入完成后核对“代码块改了吗？ref 是稳定来源吗？versions 都是 HTTPS URL 吗？”再继续下一张。

写入格式（代码块保留不删）：

```markdown
​```
---
style: 单色马克笔
ref: https://cdn.example.com/article-img-a1b2c3d4e5f6a7b8.png   # 历史上实际用过的参考图；本轮没用 --ref 就保持不变
versions:

## 联动规则：文章内容变更时主动提醒

文章内容实质性变化（机制描述改了、节点增删了、流程顺序调整了），且该章节有已生成图片时，**必须主动用 `AskUserQuestion` 告知并询问用户**（选项：重新生成 / 先保留），把现有图片放进 `preview`：

> 「[章节名] 的内容有变化，对应图片可能已过时，建议重新生成，还是先保留？」

用户选重新生成：走完整流程（质检+确认+上传+写入），新版本追加进 `versions` 数组、`![]()` 更新为新版本 URL；旧版本记录保留在 `versions` 里，不删除。

## 兼容性一览

| 场景 | 结果 |
|------|------|
| 没有可用 provider | 输出全局 `.env`/`config.json` 路径；Agent 用原生输入工具完成非敏感默认选择，文章不变 |
| Bun 与 npx 都缺失 | 打印 Bun 安装指引，跳过，文章不变 |
| Codex 未安装（仅指定 Codex 时） | 打印安装步骤，跳过，文章不变 |
| 生图脚本缺失（Codex vendored 文件） | 打印重装指引（`npx skills add/update`），跳过，文章不变 |
| picgo 未安装 | 保留画图提示与本轮结果，不写入正文、`ref` 或 `versions`，提示完成配置后重试上传 |
| picgo 未配置图床 | 保留画图提示与本轮结果，不写入正文、`ref` 或 `versions`，打印配置指引并等待重试上传 |
| 全部就绪 | 生成 → 质检 → 上传 → 用户确认 → CDN URL 写入文章 |
